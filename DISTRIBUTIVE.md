# Distributive Omaha fork

This repository is Google's open-source Omaha 3 (Google Update) adapted as the
**Distributive Update** client, installed with every DCP Worker for Windows. Built by
[omaha-build](https://gitlab.com/Distributed-Compute-Protocol/omaha-build); the server it talks
to and the operational documentation are in
[update-service](https://gitlab.com/Distributed-Compute-Protocol/update-service). Epic DCP-4967.

| Branch | Contents |
|---|---|
| `dcp/0.2.0` (tag) | The fork as shipped up to dcp-native 8.0.x: branched from Google in 2021, trusts Omaha Consulting's response key, test-signed |
| `dcp/upstream-sync` | `dcp/0.2.0` merged with Google's final Omaha 3 (`google/omaha` main, archived) |
| `dcp/distributive-keys` | `dcp/upstream-sync` plus the Distributive trust settings below; this is what omaha-build builds |

## Differences from Google's Omaha

### Identity (kept from the 2021-2023 fork; installed machines depend on these)

| Item | Value |
|---|---|
| Company and product names | `Distributive`, `Distributive Update` (`omaha/main.scons`) |
| Executables | `DistributiveUpdate.exe`, `DistributiveCrashHandler.exe`, `DistributiveUpdateSetup.exe` (`omaha/omaha_version_utils.py`) |
| Services | `distributive`, `distributivem` (`omaha/common/const_goopdate.h`) |
| Domain | `distributive.network` (`omaha/main.scons`) |
| Registry | `HKLM\SOFTWARE\Distributive\Update` and the WOW6432Node equivalent |
| Updater and product app ids | Distributive GUIDs; the DCP Worker app id equals its MSI upgrade code `{93FBCD41-FDF7-40B9-A364-99FF4A9A140F}` |

Changing any of these orphans installed machines.

### Trust (DCP-4970)

| Item | File | Value |
|---|---|---|
| Update, ping, crash, recovery, usage, device management URLs | `omaha/base/const_addresses.h` | `https://update.distributive.network/...` |
| CUP response key | `omaha/net/cup_ecdsa_pubkey.2.h`, used for **both** the production and the test-key slot in `omaha/net/cup_ecdsa_request.cc` | Key id 2: Cloud KMS HSM key, project `dcp-update-service` |
| Installer signature check | `omaha/main.scons`, bit `verify_payload_authenticode_signature` | On: downloaded installers must carry a valid Authenticode signature |
| Trusted signer | `omaha/base/const_code_signing.h` | CN `Distributive Corp.`; public key SHA-256 `4133786dfbdb382481ac93aa6fe14222c3540167ca11edc72db30de497dd4f35` (Sectigo EV certificate, valid to 2028-07-27) |

The same pin is checked by the publishing tool (update-service `trust/pins.json`).

### Build (DCP-4969, DCP-4971)

| Change | Why |
|---|---|
| `omaha/VERSION` 1.3.101.0 | Higher than the installed 1.3.99.0 so installed updaters replace themselves; build numbers must be odd |
| `third_party/libzip` at v1.9.2 | Google's final code expects 1.9.2 but left the submodule at 1.7.3 |
| `omaha/site_scons/site_tools/code_signing.py`: `OMAHA_SIGN_ARGS` | Release builds sign with exactly the given signtool arguments (SHA-256, eToken) and verify every signature; the stock signer used SHA-1 and a Google certificate thumbprint |
| `omaha/main.scons`: `GODEBUG=x509negativeserial=1` for SCons commands | The certificate tagging tool (Go 1.23+) rejects Omaha's test certificate otherwise |
| `omaha/core/scheduler_unittest.cc`: `static constexpr` | Builds with Visual Studio 2019 |
| `.github/`, `.allstar/` removed | Google's own CI configuration |

## Upstream

`google/omaha` is archived (read-only); Google's successor is the Chromium Updater. There will be
no further upstream fixes: security reports against Omaha 3 must be assessed and fixed here.
The longer-term option is DCP-4982.

## Changing trust settings

Always together with the server and publishing side; see update-service `docs/operations.md`:

- **New code signing certificate** (before 2028-07-27): add its public key hash to
  `kPublicKeyHashes` and ship the client before anything is signed with the new certificate.
- **New response key**: add a `cup_ecdsa_pubkey.<id>.h` (generated by update-service
  `tools/cup-key header`), point the key slots at it, ship the client, then switch the server.
